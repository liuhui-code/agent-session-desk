# ADR-0073：以发现记录发布作为 live Session 的可见边界

2026-11-28，已接受；关联 FL-001／004／005／013／018，细化 ADR-0002／0066／0067。实际证据见[发布阻塞项报告](../testing/results/2026-11-28-release-blockers.md)。

## 背景

新建顺序为真实后端 new-session、核对终端运行库、读取初始 pane，再以单个 option 发布完整 Session／Run／pane 发现记录。期间会话名已满足产品命名规则，发现 option 尚不存在。旧 List 把这个构建窗口当作已发布记录损坏；Windows 五轮新建与三十次并发 list 中三次出现 invalid M0 backend metadata。真实后端停在发布前也能确定复现；单看会话名不能证明可管理身份已发布。

## 决定

保留原 schema v1 option 和创建顺序，不增加注册文件、锁、轮询、重试或新 Host。空的 option 读取（允许命令行尾部 CR/LF）表示尚未发布，冷发现不把它纳入 live Session；也不据此推断启动失败、Run 已退出或可以重放新建。稍后记录发布后，下一次正常发现可验证并显示同一 Session／Run／pane。

非空的无效记录、截断、编码错误、身份不符和后端命令失败仍报错；普通空白字符不是有效的发现记录。psmux 实例在既有有界提示中保留的原记录丢失标记时，沿 omitted-original 验证返回不确定，不能复用旧记录制造 Available。冷调用不具有历史提示；Unix 原有的发现提示范围不扩大。捕获、输入、附着和停止继续要求完整有效原身份，缺标记不放行。

这是发现协议的发布边界，不是吞掉损坏记录或将失败改成空列表。冷调用没有已发布标记时不具有历史存活证明；历史仍由 SQLite 元数据提供，终端存活与 Agent 工作状态仍分开。SQLite v11、UI v7、运行库哈希、128 条发现提示和原缓存上限不变。

## 验证与范围

回归在真实构建窗口调用 List：发布前不出现伪 live Session；发布后身份不变且原进程保留；每次正常发现只读一次新目标标记，不执行错误重试。另检查非空损坏、原标记丢失、后端拒绝及未发布目标的操作守卫。模型、真实 Windows barrier 与原始并发循环分别保存 RED／GREEN。

此修复覆盖本轮复现的构建交错；原 STAB-008 那次丢失 stderr 的现场不能事后补成相同根因证明。STAB-009 原生宿主残留继续独立调查，不通过全局进程清理器或修改后端依赖转移问题。
