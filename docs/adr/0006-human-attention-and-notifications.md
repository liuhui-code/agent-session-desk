# ADR-0006：基于可信事件的人工介入提醒与分层通知

- 日期：2026-11-21
- 状态：已接受（Accepted）
- 实现与验证状态：用户已接受产品方向；提醒能力、通知适配和测试夹具尚未实现，Windows 未实测
- 关联需求：FR-14；同时约束 FR-04、FR-05、FR-08、FR-11、FR-12
- 关联功能：FL-020；涉及 FL-005、FL-006、FL-009、FL-012、FL-013、FL-015、FL-016、FL-017
- 替代 / 被替代：无；补充 [ADR-0002](0002-terminal-backends-and-attach.md)、[ADR-0003](0003-bounded-resources-and-background-work.md) 和 [ADR-0004](0004-cli-agents-and-session-messaging.md)，不改变其原有决定

## 背景与约束

用户在一个会话中工作时，另一个 agent 可能停在批准、提问或需要检查的异常处。逐个切换检查增加负担；短暂横幅又容易错过，因此需要可回查、可定位的待处理记录。

首版采用简约列表与全屏 attach。进入 agent 后管理器导航隐藏，仅给 Tab 加标记无法覆盖此场景。自定义 CLI 也不一定提供状态事件，不能承诺任何 CLI 都可被准确识别。

用户已要求将上一轮讨论的提醒方案加入 Feature Ledger、ADR 和测试设计。本决定接受该产品方向，同时保留事件合同、Windows 通知实现和数值预算的验证门槛。

## 决定

### 1. 将人工介入作为独立能力

建立关联会话的“待处理事项”，区分需要用户采取行动与一般结果通知。下列名称为产品概念，最终接口字段与枚举另行固定。

| 类型 | 可以表达的事实 | 默认呈现 |
| --- | --- | --- |
| 待批准 | 有可信来源报告一项需要用户决定的操作 | 会话标记与待处理入口 |
| 待回答 | 有可信来源报告需要补充信息、选择或答复 | 会话标记与待处理入口 |
| 异常待检查 | 有明确运行异常或需检查事件及其依据 | 原因与待处理入口 |
| 结果待查看 | 有对应结果或完成证据 | 与阻塞事项分开；主动完成通知默认关闭 |
| 疑似需要处理 | 仅终端文本规则等启发式命中 | 明确标为疑似，不冒充已确认事项 |
| 状态未知 | 缺少可靠信号，或观测链路中断 | 显示未知及原因，不制造批准、完成或空闲证据 |

人工介入、进程存活、工作忙闲和消息投递状态分别记录。一个会话显示待处理不表示整个 agent 的所有后台工作都停止；普通 `ready` 也不自动证明某条人工请求已解决。

待批准、待回答属于需要活 Run 接收的交互请求；异常待检查属于用户诊断事项。Run 结束使前者失效，但异常退出本身可以产生绑定该已结束 Run 的待检查事项，用户仍可打开历史核查，不能因 Run 已退出而删除它。

### 2. 按状态来源决定可信程度

优先接收经过适配验证的结构化事件、原生 hook，或合作式自定义 agent 主动上报。启动仍使用 CLI；这些信号不是基础终端接入的前置条件。

来源绑定必须核对产品作用域、Session 和 Run，不能只相信事件正文自报的会话名称。终端正文中出现类似 JSON、批准关键词或历史提问，不直接取得控制事件资格。

可选的文本识别只产生疑似提示，并注明规则来源；不能凭滚动历史里的旧提示持续重复报当前请求。无输出时长、低 CPU、shell 或后台存在，都不能单独证明需要人工介入。

能力声明应说明是否支持可靠人工介入事件、对应请求的结束事件及状态重查。仅支持进入事件的接入不得假称已经自动掌握事项结束；无法确认时保留待核实状态。

### 3. 保留事项身份、证据与顺序

待处理事项绑定 `session_id + run_id + attention_id`，其中 `attention_id` 表示一次独立人工请求。来源事件另有可去重身份与版本/顺序证据；这些是合同要求，不规定当前数据库字段或传输格式。

- 同一请求的重复事件只更新同一事项，不按轮询次数新建提醒。
- 两次不同请求即使正文相同，也分别保留，不能仅按文本哈希合并。
- 重命名、排序、分组及关闭视图不改变寻址目标。
- 迟到、乱序或重放的旧事件不能让已经结束的旧事项再次变成待处理。
- 请求结束先于创建事件到达时，仍需依据有效身份与顺序避免随后复活；保留与清理规则在事件合同中确定。
- 确认 Run 结束或被替换后，该 Run 的活跃交互请求失效；后续创建的新 Run 不继承这些请求的可执行入口。诊断事项保留其历史目标和检查状态。
- 仅失去连接、漏事件或超时不等于 Run 结束，也不等于事项解决；保留最后已知记录，注明观测不确定并在重新接入时核对。

事件接收、记录持久化、通知投递是不同边界。对外确认记录已保存时必须有对应持久化证据；恢复不能凭数据库旧值推断系统通知从未发出。

### 4. 已查看、稍后提醒和已解决分别处理

| 行为或证据 | 允许的变化 | 不允许推断 |
| --- | --- | --- |
| 打开待处理项或进入目标会话 | 记录已查看 | 用户已回答、已批准、agent 已继续 |
| 关闭系统横幅 | 关闭该展示 | 应用内事项已解决 |
| 稍后提醒 | 暂缓提醒展示 | 请求被取消或工作状态变为 ready |
| 用户隐藏 / 关闭一条提醒 | 记录人工隐藏动作与来源，保留事项事实 | 伪造 agent 的解决回执 |
| 用户对诊断事项显式“标记已检查” | 结束该检查事项，记录人工检查来源 | 交互请求已获批准、agent 已收到回答或任务已成功 |
| 收到对应请求已处理的可信事件 | 结束该事项，保留依据 | 所有同会话事项或整个任务均完成 |
| 收到撤销事件 | 结束对应事项并标记撤销 | 用户已经批准 |
| 取得原 Run 结束证据 | 使原 Run 的活跃交互请求失效；保留或创建适用的诊断事项 | 后续 Run 已处理这些问题，或异常已经检查 |

待处理汇总必须与事项事实一致，已读不能自动从未解决事项中删除。若界面同时显示会话数和事项数，应明确计数单位；同一会话的多条事项仍可分别查看。记录应区分来自 agent 的解决证据与用户明确完成诊断检查；最终字段名未固定。

### 5. 简约界面与全屏 attach 的提醒路径

管理界面在会话行显示符号与短文字，并提供一个“待处理”汇总入口；详情按需打开，不常驻新增通知侧栏。状态不能仅靠颜色表达。

用户可以选择目标事项或执行“下一个待处理”动作。固定键位需经过 Windows Terminal、IME、psmux 和实际 agent 的冲突验证，不沿用未经验证的概念快捷键。

监测逻辑与 TUI 绘制分离。管理器仍运行但已进入全屏 attach 时，应继续处理已支持的事件；不能因为绘制循环暂停就声称没有新事项。

attach 期间通过已启用的系统通知，或单独验证的终端提醒告知用户。通知到达不向 agent 画面插入提示文字、不抢输入焦点、不自动切换会话，不修改终端尺寸或当前草稿。

点击“查看”是用户明确导航请求：重新核对作用域、Session、Run 和事项当前状态，再按既有终端交接规则定位。旧交互请求失效时显示原因；绑定已退出 Run 的诊断事项进入该 Run 的历史与错误记录。记录缺失或目标未知时明确说明，不按名称寻找替代对象，不自动重启 agent。

通知入口不发送批准、答案或 Enter。用户进入原 CLI 后处理，仍使用其实际交互和权限机制。

### 6. 系统通知是可选展示渠道

应用内待处理记录是可回查的主要记录。桌面通知、声音和完成通知分别可选，默认关闭；启用桌面通知后仍可保持无声。本产品设置不改写用户全局终端配置，也不保证屏蔽 agent 自己产生的铃声。

系统通知表达会话和事项类型，详细正文按需查看；标题和来源文本始终作为数据处理，不拼接成 shell 命令或不受控的激活参数。通知文本的字段、长度和可见范围在策略合同中固定。

Windows 通知被关闭、免打扰、发送失败或未展示时，应用内事项仍保留。系统 API 接受通知不能记为用户已看到或事项已处理；能力不可用时明确说明当前渠道限制。

同一有效状态转变去重，多个会话同时触发时可以汇总展示，但逐项记录不能被汇总丢弃。通知失败后的重试、崩溃后的投递不确定与再次提示规则需要有界，不能承诺系统横幅端到端 exactly-once。

BEL 可作为经过验证的可选辅助，其实际效果取决于 Windows Terminal 配置和 psmux 传递；它不能携带完整事项记录，也不能代替应用内定位。首版不依赖始终可见的 psmux 状态条。

### 7. 与后台 Host、消息队列和资源的关系

| 阶段 | 提醒职责 | 必须声明的边界 |
| --- | --- | --- |
| M2 | 管理器存活期间接收事件、持久记录、显示和定位；验证全屏 attach 中的 Windows 提醒路径 | 不因隐藏 UI 停止已承诺监测；不要求新增产品常驻服务 |
| M3 | 复用一个共享轻量 Host，在启用后台提醒时持续接收事件、处理通知与恢复 | UI 退出后的监测需有实际运行的消费者及独立证据 |
| M4 | 在干净 Windows 发布环境复验通知注册、激活、旧通知、升级及渠道降级 | 发布说明按真实环境列出支持、可选和不可用能力 |

psmux 保持终端运行不证明人工介入仍被监测。没有消费者时，保留已存记录并说明监测暂停；重开后按已支持来源重新核对，不虚构停机期间完整事件历史。

经过单独验证的 agent hook 可以提供可选后台通知路径，但不能推广为任意 CLI 都支持。若 hook 与共享 Host 同时启用，须有明确归属与去重策略，不能双重不断弹出。

通知由既有共享核心和平台适配承担，不为每个会话启动常驻服务，不靠 LLM 持续读取屏幕判断状态。优先事件触发，必要回查有界，不为监测后台会话持续渲染完整预览。

审批等人工输入等待期间，普通跨会话自动投递继续暂停；处理通知本身不获得输入所有权。解除暂停仍需满足 ADR-0004 的真实就绪、目标一致和输入占用条件。

待处理数量、单事件尺寸、持久记录保留和提醒延迟均需有边界。拥塞或磁盘失败不能静默丢弃已确认持久化的事项；具体拒绝、合并展示与恢复策略在相关合同中固定。

## 比较过的方案

| 方案 | 取舍 |
| --- | --- |
| 仅给 Tab 加红点 | 管理界面可用，但全屏 attach 隐藏导航时无法满足及时发现需求 |
| 每次轮询发现 waiting 都弹通知 | 重复状态会刷屏，无法区分新请求；采用按事项与事件去重 |
| 所有 CLI 靠静默或关键词确认等待 | 无法分清长任务、旧日志和真实请求；未知保留未知，文本规则只作疑似辅助 |
| 收到事件自动切换并代为批准 | 会打断当前输入，也改变原 agent 的决策流程；通知仅提示和定位 |
| 仅依赖系统横幅 | 关闭、错过或系统未显示时无法回查；持久待处理记录与展示渠道分开 |
| 每会话一个通知进程 | 增加资源、所有权与故障成本；复用既有共享核心及单一 Host |

## 后果与代价

用户可以集中找到需要处理的会话，在其他工作进行中及时发现阻塞。应用需要新增事项模型、持久化、来源适配、通知去重、Windows 平台展示与激活处理，并承担重连和多实例协调责任。

通用终端接入保持可用，但准确提醒能力按 agent 和适配版本声明。缺少可靠结束事件的接入可能需要用户回到原 CLI 核实，不能为了清除标记而伪造已解决。

系统提醒的可见性受用户设置与平台行为影响；产品应提供可回查状态和诊断，不能承诺横幅一定被看到。预算建立前不宣称具体毫秒时延或内存上限。

## 验证与重新评估

测试设计映射见 [FL-020 覆盖](../testing/COVERAGE.md#fl-020)，设计不代表已经执行或通过。

1. 用户在 A 输入时，B 报告审批：B 的事项可发现，A 的焦点、输入字节和画面不被提醒改写。
2. 查看、关闭横幅或稍后提醒后，未解决事项仍在；交互请求只按有效解决/撤销证据结束。对诊断事项显式“标记已检查”只结束该检查，不产生批准、回答或任务成功证据。
3. 覆盖重复、乱序、延迟、同文不同请求、解决先到、旧 Run 和会话重命名；无旧事项复活或错目标导航。
4. 覆盖断连后重查、Run 退出、Host 崩溃、存储失败以及通知发送后未记回执的窗口，保留不确定性与可回查记录；Run 退出使旧交互请求失效，但异常退出的待检查事项仍可定位历史。
5. 审批与普通消息队列同时存在时，不出现自动批准、Enter 或任务正文误入审批输入。
6. 在原生 Windows 验证通知关闭、免打扰、点击过期通知、全屏 attach、中文/特殊字符和多会话同时提醒。
7. UI 退出后分别验证有共享 Host、无消费者及可选 hook 组合；无消费者不声称持续监测，多个入口不重复刷屏。
8. 记录事件峰值、长时间重复通知、提醒延迟和全进程树资源；先建立预算，再判断达标。

若选定 Windows API 无法满足目标安装方式、权限组合或资源预算，固定最小复现后评估另一平台适配；若某 agent 的信号不可靠，降级该接入能力并保留未知。只有改变全屏 attach、Host 进程策略或通用 CLI 接入要求时，才另立替代 ADR；不能通过扩大本条隐式改变这些决定。
