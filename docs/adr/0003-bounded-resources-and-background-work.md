# ADR-0003：限制常驻资源，持久化记录，按阶段引入消息 Host

- 日期：2026-11-21
- 状态：已接受（Accepted）
- 实现与验证状态：M0 有界捕获/选中预览和私有后台配置已编码；内存基线、存储、已接受预算与 Host 尚未完成
- 关联需求：FR-03、FR-05、FR-06、FR-07、FR-08、FR-09、FR-10、FR-12

## 背景与约束

用户把低运行内存与简约体验列为主要要求。终端后台、备用 shell、agent 和多份输出历史均会占用资源，不能只比较 UI 框架语言或可执行文件大小。

## 决定

### 有界资源

- 只为当前可见会话刷新正文预览，后台会话使用必要的低频状态检查或经过验证的事件通知。
- 对输出尾部、屏幕缓存、待处理事件和消息尺寸设定明确上限。按字节及实际对象成本计量，不只限制行数。
- 长期输出写入有轮转与保留上限的文件，查看时分页读取；不在 UI、每个 Tab 和后台重复保存完整历史。
- 显示可以合并刷新，指令与控制事件必须保持顺序；发生记录缺口或截断时显式标记。
- 不预热闲置 agent，不随本产品默认开启 psmux 备用 shell 池或待命 server。

### 产品专用后台配置

本产品启动的 psmux 子进程使用 `PSMUX_NO_WARM=1`，并通过独立 namespace、数据目录与配置文件设置 `warm off`。不修改用户全局环境或现有 psmux 配置。已运行的后台是否接受新配置，需要明确重启/重载流程。

稳定版本的环境、配置优先级和关闭预热后的实际进程树进入 M0 验证。不能仅设置一个 pool 大小就假设所有待命进程已经消失。

### 存储职责

| 数据 | 选择 | 尚需确定 |
| --- | --- | --- |
| 启动配置、主题与偏好 | TOML 文件 | 配置 schema、解析库与迁移规则 |
| Session、Run、消息与回执 | SQLite 3 | Go 驱动、事务边界、锁与恢复、缓存预算 |
| 终端输出记录 | 有上限的本地文件 | 格式、索引/游标、轮转、截断和清理策略 |
| 当前画面与短尾部 | 有界内存缓存 | 按实测制定预算 |

SQLite 选择不等于已选择 Go 驱动或启用某种 journal 模式；这些细节随 Windows 构建、并发和内存验证确定。

首个 M0 切片仅使用后端 user options 保存少量活跃 Session/Run 标识，用于重新发现托管终端。该信息随后台存在，不构成产品历史仓库；没有用另一种文件格式或后端选项替代 SQLite 的持久化方向。当前尚未实现 TOML 配置、SQLite 元数据/消息、连续输出日志与轮转，相关功能继续按 M1–M3 推进，见 [M0 开发说明](../M0_DEVELOPMENT.md)。

终端后台继续处理输出不表示应用日志始终连续写入。关闭 TUI 且无自有消费者时，可读范围依赖后端已保留的历史或经验证的日志能力；缺口、轮转与未采集区间必须显式标记，不能承诺完整聊天历史。

### 进程阶段

M0–M2 的默认形态为按需运行的 TUI/CLI + 终端后台。会话核心作为共享代码运行，不为每个模块启动服务。退出 TUI 后由 psmux/tmux 持有终端，持久化记录保留。

M3 先实现读取、显式发送和落盘队列；管理 CLI 按需调用本身不要求常驻 Host。没有消费者时队列保持待投递，关闭 TUI 不声称自动处理仍在继续。

实现 FR-08 的后台自动消费、持续事件处理与统一投递仲裁时，引入**一个共享轻量 Host**。它只负责消息策略和元数据，不重复托管 ConPTY。M3 完成必须包含可靠就绪信号下的自动投递验证；“暂不常驻 Host”不能成为删除 FR-08 的理由。

所有发送入口必须共享跨进程的目标校验与串行投递规则；不能依赖某个 TUI 进程内的锁防止其他 CLI 并发写入。全屏 attach 中默认暂缓自动投递，直到明确交接输入控制；无法确认占用时保留等待，自动投递不得与用户编辑交错。

## 首批实施记录（2026-11-21）

UI 当前只保留选中会话的屏幕文本，设置 64 KiB/200 行的防御性保留上限；只为可见预览请求捕获，切换、help、attach 与退出时取消读取，并等待旧捕获结束后再开始新的请求。后端命令也有输出和执行时间边界。私有 psmux namespace、目录、配置与关闭预热的环境设置已编码，但实际后台进程树须由 Windows 验证。

这些固定上限是当前实验切片的实现边界，不是已接受的性能预算，也不能证明多会话长期运行内存稳定。本轮没有新增产品常驻 Host、消息消费者或通知服务；未采集 Windows 全进程树内存，也未完成长稳测试。具体代码、单元证据与待测项见 [M0 执行报告](../testing/results/2026-11-21-m0-source-migration.md)。

## 比较过的方案

- 一开始增加通用常驻服务：为未来功能提前增加进程、连接和故障恢复责任，首个切片收益有限。
- 只在 UI 内存保存队列：UI 退出会丢失请求，不满足通信与重连要求。
- 全部历史常驻内存：实现读取方便，但内存随会话数量和运行时长增长。
- 首版重构 psmux 为共享后台：可能减少进程，但增加映射、隔离和接口兼容改造，先以实测决定必要性。

## 验证与重新评估

测试 0、1、5、10 会话的空闲、单会话持续输出、全部持续输出，以及退出/重开管理器。分别报告 TUI/可选 Host、psmux server/client、控制台辅助进程/shell、agent 本身；同时报告工作集、私有内存和相对直接运行同一 agent 的增量。

持续输出后内存应达到可解释上限，记录窗口尺寸、负载和保留策略。M0 先建立基线，再确定数值预算；没有实测前不发布 MB 承诺。若后端进程数占主要成本，再评估共享映射；若显示缓存占主导，先调整缓存和刷新策略。
