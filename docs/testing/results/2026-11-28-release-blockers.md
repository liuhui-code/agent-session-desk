## 反馈循环与发现边界

在新的私有安装创建最多一个 Go 夹具 Run，同时六个独立 CLI 执行 list；保存每次 stdout、stderr、启动到观测结束耗时及退出码，不重复 start。五轮／三十次读取出现三次真正的 exit 1，均为 read live session … invalid M0 backend metadata；五次 start 均成功，最终夹具为 0。

第一版驱动未保留异步 Process.Handle，prime 的 ExitCode 为空，虽然 stdout 为正常空发现；该轮是驱动错误，不算产品复现。保留原件，在新目录先取得句柄再 WaitForExit，才得到上述三次真实非零。耗时为启动到结束观测的墙钟时间，包含调度等待，不能冒称 CPU 或纯后端时延。

按顺序验证三种可能：尚未发布；非空标记损坏；已有标记偶发读空。在真实 psmux 创建进程但故意不执行发现 option 发布，旧代码确定返回同样元数据错误；Windows RED 0.68 秒，原夹具经精确目标清理。这个真实协议边界与 StartRun 中调用顺序一致，不替换成假后端。普通 helper RED 也保存。

修正仅把没有发布记录的新目标留在发现集合之外；发布后读取原身份。非空损坏、超限、命令失败、旧标记丢失及目标操作仍保守拒绝，不增加错误重试。最终 Windows 四个顶层／七个含子测试全部通过，无失败或跳过，其中真实发布边界 0.89 秒。五轮三十次同样并发读取全部成功，五次 start 成功、最终夹具为零；不是增加 retry 后的成功。当前诊断产物基于 b255d91 的工作树，文件／字节指纹见证据目录，不作为干净发布包。
